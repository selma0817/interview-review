# Interview Review — v2 spec: the learning loop

Date: 2026-11-13
Status: **approved 2026-11-13.** Phase 1 is complete: FSRS shipped 2026-11-13; deploy on push and `main` protection shipped 2026-11-18. Phases 2–4 are not started.
Replaces the v1 parts about the setup screen, "needs review", completion, and how the bank is made (`cs-review-v1-spec.md`).

## 1. Goal

One loop for learning CS concepts and keeping them:

1. **Learn**: learn a concept with Claude Code, which writes and links the note in the Obsidian vault (`knowledge_base`, published as `selma0817/cs-knowledge-base`).
2. **Interview**: an LLM uses the vault to run an interactive mock interview.
3. **Distill**: at the end of a learning or interview session, the LLM proposes cards from what came up. You answer yes/no on each, and approved cards are published.
4. **Refresh**: https://selma0817.github.io/interview-review/ schedules daily review with FSRS.

**Terms.** A *card* is one entry in the bank. The JSON and code keep the v1 name `questions` to avoid churn.

### Principles

- **One-way flow: vault → cards.** A card is a snapshot of the note when it was made. Editing a note never re-checks, changes or removes cards. Cards are added, edited and removed only in the bank.
- **Note first.** Every card's answer is supported by a section of a note. If the answer isn't in a note yet, the note is updated first.
- **Correct at creation.** Nothing re-checks a card later, so every card passes three checks before you see it, and your yes/no is the last gate.
- **The site is private review.** Nothing reads your progress back: no sync, no backend, no MCP.
- **Each phase is usable on its own**, and ships with tests green.

## 4. Card format (schema 2.0.0)

`bank/raft.json`:

```json
{
  "topic": "Raft",
  "questions": [
    {
      "id": "raft-k3x9qa",
      "version": 1,
      "type": "single_choice",
      "topics": ["Raft"],
      "difficulty": "hard",
      "question": "A term-7 leader sees an uncommitted term-6 entry on a majority…",
      "options": [{"id": "A", "text": "…"}, {"id": "B", "text": "…"}],
      "answer": "B",
      "explanation": "…",
      "sources": [{
        "path": "Concepts/Distributed Systems/Raft/Raft Commitment and Application.md",
        "heading": "Why direct commitment requires the current term",
        "blob_sha": "<filled by script>",
        "url": "<filled by script, pinned to the vault commit>"
      }],
      "created": "2026-11-14",
      "provenance": "You said a majority alone is enough to commit an old-term entry.",
      "checks": {"grounded": "pass", "blind_answer": "pass", "code_run": "n/a"}
    }
  ]
}
```

- **Topics:** `topics` is the union of the cited notes' `topic/` tags (first note first), copied by `bank:add`; `bank:validate` rejects topics not in `bank/topics.json`. The file-level `topic` is the card's first topic.
- **Types:** `single_choice`, `flashcard`, `short_answer`, `code_reading` (as in v1). Optional fields: `rubric` (3–5 checkable points), `code_language`, `extension_note`.
- **Dropped from v1:** `review_status` (every card in the bank is approved), `grading` (implied by the type), `language` (always English).
- **New:** `created`, `provenance` (the session moment it came from), `checks`.
- **ID:** `<topic-slug>-<6 random lowercase base36 chars>`, made by the script. It is rejected if it already exists in the bank or in `retired-ids.txt`. Why: progress is stored by `id@version`, so a reused ID would hand a new card the old card's FSRS memory.
- **Version:** starts at 1. It is bumped only when you confirm a card's meaning changed (the LLM proposes; you decide). **A version bump resets that card's FSRS state.**
- **Built file:** `bank:build` merges every `bank/*.json` into `public/questions.json` as `{schema_version: "2.0.0", built_at, questions: [...]}`. It runs as part of `npm run build`.

## 5. Phase 1 — Site: FSRS daily refresh

### 5.1 Library

- **`ts-fsrs@5.4.2`, pinned exactly** (FSRS-6, MIT, no dependencies, Node ≥ 20).
- **Not 6.0.0 yet.** 6.0.0 was published 2026-10-28. It is a major rewrite (FSRS-7 by default, an async `DefaultScheduler`, a new `srs-kit` dependency) and requires **Node ≥ 24**, while this repo pins Node 22.
- **Upgrade path:** we keep the **complete review log** from the first review. ts-fsrs 6's migration guide needs exactly that history to rebuild memory for FSRS-7 (`Reschedule.replay`), so upgrading later stays possible.
- **Parameters:**
  - `request_retention: 0.9`
  - `maximum_interval: 180` days (open item §10)
  - `enable_fuzz: true`
  - `enable_short_term: true`, with the default learning steps `1m, 10m` and relearning step `10m`

### 5.2 Storage

- **Key:** `interview-review:fsrs:v1` in localStorage:
  ```
  { storageVersion: 1,
    cards:    { "<id>@<version>": ts-fsrs Card, dates as ISO strings },
    log:      [ ts-fsrs ReviewLog + key ],     // never trimmed
    newIntroduced: { "<YYYY-MM-DD>": count },
    settings: { topics, types },
    session?: { kind: "today" | "practice", queue, cursor } }
  ```
- **Old key:** the v1 key `cs-review:progress:v1` holds only test clicks and is deleted on first load.
- **Reset** removes only the new key.
- **Size:** about 30 reviews a day for a year is roughly 11k log entries, under 1 MB, well within localStorage limits.
- **Corrupt or unreadable storage** starts clean, with a notice, as in v1.

### 5.3 Home screen

- **Due today:** started cards whose `due` is before the end of local today.
- **New:** cards never reviewed, capped at **10 newly introduced per local day** (open item §10). Bank order, oldest first.
- **Start today's review:** due cards (oldest due first), then new cards.
- **Per topic:** due count and total.
- **Practice a topic:** the topic and type filters. The queue is every card in the filters, lowest current recall chance first (`get_retrievability`), new cards last. Ratings count normally.

### 5.4 Card flow

- **Multiple choice:** submit.
  - **Wrong** → Again is recorded immediately, the explanation shows, then Next.
  - **Right** → Hard / Good / Easy, with Good focused.
- **Flashcard, short answer, code reading:** Show solution → Again / Hard / Good / Easy.
- **Each button shows its next interval** from `f.repeat(card, now)`, e.g. `Good · 4d`.
- **A rating saves immediately**, so refreshing never loses it.
- **Same-session repeats:** a learning or relearning card that falls due within 20 minutes (Anki's learn-ahead limit) goes back into the current session's queue. Otherwise it waits for a later session.
- **Card header:** "Reviewed N times · forgot M" from `reps` / `lapses`, replacing v1's attempt history.

### 5.5 Removed

The "Mark as needs review" button, "Review marked questions", the completion %, and "Practice new questions".

### 5.6 Session summary

Count per rating, plus when the next card is due.

### 5.7 Tests

- **Unit, with a fixed clock:**
  - A wrong multiple-choice answer records Again.
  - Due and new counts are correct.
  - The new-card cap resets at local midnight.
  - Learn-ahead puts cards back in the queue.
  - A version bump gives a fresh card.
  - Corrupt storage starts clean.
- **e2e:**
  - Rate cards → reload → the state persists and the due count dropped.
  - Topic practice records ratings.
  - Run at desktop and mobile widths.

### 5.8 Publishing on push: your CI/CD hands-on exercise ✅ done 2026-11-18

Deploying on push turns the pipeline into continuous **deployment**: no human between green `main` and the live site. That makes the holes from our CI/CD rounds matter. You write this change and I review it. Acceptance criteria:

1. Deploy runs only after **all** checks pass, including e2e: a **gate**, not a report.
2. It deploys **the exact build that was tested**, not a fresh rebuild.
3. Only `main` deploys, and the `pages` concurrency group stays.

**Result** (PR #1, squash commit `be00445`):
- `ci.yaml` runs on `pull_request` and `workflow_call`. Its last step packs the tested `dist/` with `upload-pages-artifact`, only when not on a PR (`github.event_name != 'pull_request'`). → criteria 1, 2
- `deploy.yaml` runs on push to `main` and `workflow_dispatch`. Job `ci` calls `ci.yaml`; job `deploy` (`needs: ci`, `if: github.ref == 'refs/heads/main'`) only runs `configure-pages` + `deploy-pages`. → criteria 1, 2, 3
- First automatic deploy: merge at 00:41:07 → live at 00:41:58 (Deploy run 44209837554).
- `main` ruleset: PR required (0 approvals), required check `checks` from GitHub Actions, up to date, no deletion or force push, empty bypass list. A direct push to `main` was tried and rejected with `GH013`.
- A second guard on deploying from other branches: the `github-pages` environment only allows `main`.

## 6. Phase 2 — Distill skill and bank scripts

### 6.1 Vault conventions (`knowledge_base/CLAUDE.md`)

- **Common mistakes:** `## Common mistakes` → `### Mistake N: <the wrong belief>`, with the body giving the correction (plus a counterexample or failure scenario where there is one).
- **Your own mistakes:** add ` (mine)` to the heading. The 55 existing entries stay unmarked unless you mark them.
- **Sources:** key claims, numbers and formulas link a primary source (paper, official docs).
- **Language:** English body. Chinese aliases are fine.

### 6.2 Scripts (in `interview-review`; `--vault` defaults to `../knowledge_base`)

- **`bank:add <drafts.json>`**
  - Validates the drafts.
  - Checks every source:
    - the path exists at vault `HEAD`
    - the heading exists as a markdown heading in that file
    - the file has no uncommitted changes
    - vault `HEAD` is pushed to `origin/main`, so the pinned URL resolves
  - Fills in `blob_sha` (`git rev-parse HEAD:<path>`) and the pinned URL.
  - Assigns IDs, appends to `bank/<slug>.json`, and runs `bank:build`.
  - Doesn't commit.
- **`bank:remove <id>…`:** removes the cards and appends their IDs to `retired-ids.txt`.
- **`bank:build`:** merges and validates. Checks include:
  - the schema
  - unique IDs, including against the retired list
  - each multiple-choice answer exists among its options
  - each source has `blob_sha` and a URL
- **`bank:validate`** replaces `validate:bank`, and CI runs it.

### 6.3 Distill skill (`.claude/skills/distill/`)

**Trigger:** you say "distill", or I offer it at the end of a learning or interview session.

1. **Collect** what the session exposed: misconceptions you showed, failure scenarios you couldn't give, definitions, code behavior.
2. **Note first.** If an answer isn't in a note section, propose the note edit (a section, or a `(mine)` Common mistakes entry). After your OK, apply it, commit and push the vault.
3. **Draft up to 8 cards.** The type follows where the card came from:

   | From the session | Card |
   |---|---|
   | A misconception | Multiple choice with your wrong belief as one option |
   | A failure scenario you couldn't give | Short answer with a rubric |
   | A definition | Flashcard |
   | Code behavior (leak, race, output) | Code reading |

4. **Run the checks.** A failed card is fixed and re-checked once; if it still fails, it is dropped and I tell you.
   1. **Grounded:** the cited section supports the answer and the explanation. The script also confirms the heading exists.
   2. **Blind answer:** a fresh subagent sees only the section, the question and the options. It must pick the keyed option and find no second defensible one.
   3. **Code run:** the snippet is actually run (`go run`, `node`). A fragment gets a minimal harness. If it can't run (for example, it needs a cluster), it's marked `n/a` with a reason you can see.
5. **Present** a numbered list. Each card shows its type, question, options/answer, explanation, source, session moment and check results.
6. **You reply** `keep 1 3 4 · drop 2 · edit 5: …`. Edited cards re-run the checks.
7. **Publish:** on a new branch, `bank:add` → `npm test` → commit `Add N cards: <session topic>` → push the branch → open a PR. CI must pass (`main` is protected); you merge, and the merge deploys automatically. I report the PR link, and what went live after you merge.

**Style guide (`style-guide.md`):**
- Prefer failure scenarios ("what breaks if…") over definitions.
- Wrong options are real misconceptions, yours first.
- One idea per card.
- Answers of about 5 lines or fewer; rubrics of 3–5 checkable points.
- English only.
- Numbers only when they matter (e.g. your GRPO mixed-group 72% → ~50%).

**Editing and removing cards:** you ask in a session. For an edit, I say whether it changes the card's meaning (→ version +1 → FSRS reset), and you confirm.

**First run:** the answer keys from the CI/CD and search rounds, stored in my memory folder, go through the same checks and your yes/no.

## 7. Phase 3 — Interviewer skill (`.claude/skills/interview/`)

- **Reads only the vault:** notes, `[[links]]`, Common mistakes, the MOC, and the bank's card list (to find thin areas). It never reads site progress.
- **Picking a topic:** you name one. Or it offers 3, drawn from your `(mine)` mistakes, notes changed in the last 14 days (`git log`), and MOC areas with the fewest cards.
- **Style:**
  - One question per message (at most about 3 small tasks).
  - Start at the conclusion, then push with "what breaks if…" and counterexamples.
  - Follow `[[links]]` for the next question.
  - When you're not sure, switch to fill-in or multiple-choice steps using real data from the note.
  - Grade against the note and cite the heading.
- **No note, no grading:** if a topic has no note (e.g. Tool Calling), say so and offer a learning session first, instead of grading from my own knowledge.
- **Recording:** propose new misconceptions as `(mine)` entries. With your OK, write them and commit.
- **At the end,** offer to distill.

## 10. Open items (defaults in bold; confirm or change)

1. Maximum interval: **180 days**. ts-fsrs's default is 36500 (100 years). For interview prep, half a year without seeing a card seemed like enough.
2. New cards per day: **10**.
3. Learn-ahead window: **20 minutes**.
4. v1 questions: **migrate, check and review** (vs drop them).
5. ts-fsrs version: **5.4.2**. This changes what I said on 2026-11-13, where I named 6.0.0 before reading its changelog.
